# PRD 인터뷰 기록

상태: 사용자와 질문 하나씩 논의하며 만드는 작업 기록. 기존 index.html은 참고 초안이며 승인된 PRD가 아니다. 명시적으로 정해지지 않은 기능·기술·범위는 제안으로 유지한다.

## 이미 합의한 출발점
- A/B 테스트의 설계·분석·판단에 집중하며 CRM 전체 관리 도구는 만들지 않는다.
- 전체 승패와 세그먼트 차이를 중요하게 다룬다.
- 전자책에서 발전하는 도구다.
- PRD는 사용자와 문답으로 구체화했다. Q10 답변에서 남은 Q11~Q20은 미라 권장 방향으로 선택하도록 위임받았다.
- HTML은 문서·프로토타입에 쓸 수 있는 형식이며 최종 계산·저장 구조는 미확정이다.

## Q01 가장 중요한 사용자 변화
사용자 원문:
> 실제 실무에서도 사용하고 일상생활에서도 허들없이 쉽게 사용할 수 있는거 만들고 싶어. LLM 연결해서 자연어로도 가능하게
> 1. 결과를 보고 승패와 고객군 차이를 제대로 이해 > 실험을 시작할 때 설계에 확신이 생기는 > 그 결과로 무엇을 할지 결정하기 쉬워지는 것

확인된 우선순위:
1. 결과와 승패, 고객군 차이의 정확한 이해.
2. 실험 설계에 대한 확신.
3. 결과를 바탕으로 한 다음 행동 결정 지원.

추가 요구:
- 업무와 일상에서 진입 장벽이 낮은 사용 경험.
- LLM을 연결한 자연어 사용.

미확정 항목(이후 답변으로 갱신):
- 일상 예시로 '지하철 도착 문구를 어떻게 표현하면 좋을까?'가 제시됨. 업무 밖 사례의 상세 지원 범위와 통계 설계는 미확정.
- 자연어로 상황만 주면 도구가 방향, A/B 후보와 시험 방법을 함께 제안하길 원한다고 확인됨.
- 데이터가 없는 질문에는 방향·설계 제안을 제공하고, 실제 결과 판정과 구분하는 원칙은 설계 제안으로 유지.
- 단순 전후 관찰·개인 반복 측정의 분석 지원 범위는 미확정. 실험 배포·수집은 Q04에서 초기 버전 제외로 합의.

## Q02 자연어 진입의 구체 사례
사용자 원문:
> 지하철 도착 문구 어떤식으로 표현하는게 좋을까? 이런느낌으로 말해도 되나?

해석: 비교할 두 안이나 지표를 몰라도 상황 설명으로 시작하는 경험을 원함. 실제 지하철 운영 안내를 변경한다는 승인은 아니며, 모의 화면·시험과 실제 운영의 범위는 구분함.

## Q03 후보·방향·시험 방법 제안
사용자 원문:
> 아직 비교할 A/B 문구도 정하지 않은 상태에서, 도구가 후보를 제안하고 시험 방법까지 함께 잡아주길 원해. 자연어로 상황만 주어질 때는 방향성을 잡아주는거 어때? 방향성에 안 맞나?
> 그리고 뒤에 나올 질문일 수도 있지만 내가 만들 tool은 위너 선정 기준, 어떤 지표로 분석? 어떠한 비율로 측정? 비율은 사용자에게 물어보는게 맞나? 다양한 변수들은 어쩌지?

확인된 요구:
- 상황 설명 → 목적 구체화 → 비교 후보·시험 방법 제안까지 자연어 안내에 포함.
- 승자 기준·분석 지표·비율·변수 처리를 사용자가 처음부터 통계 용어로 정해야 하는 흐름을 재검토.

이번 설계 제안(확정 전):
- 사용자는 목적·현실 제약·감수할 위험을 설명하고, 도구는 지표·분모·배정·판정 계획을 제안해 이해 가능한 요약으로 확인받음.
- 배정 비율, 지표의 분자/분모, 기준율·목표 효과, 통계 오류 기준을 구분.
- 바꿀 조건, 동일하게 유지할 조건, 무작위화/블록으로 다룰 배정 전 요인, 사전 분석 집단, 결과·보호 지표를 역할별로 분류.
- 결과 전 계획과 결과 후 변경을 기록하고, 데이터 없는 상태에서 승자를 확정하지 않음.
- 당시 실험·설문 배포와 데이터 수집 범위는 미결정이었다. 이후 Q04에서 초기 버전은 외부 실험으로 합의.

## 합의 갱신 — 자연어 안내 흐름과 네 원칙

사용자가 다음 흐름으로 진행한다고 명시했고, 직전 답변 1~4를 꼭 저장해 달라고 요청함.

상황 설명 → 목적 확인 → A/B 후보 제안 → 지표·배정·판정 계획 추천 → 사용자 확인 → 결과 분석과 설명

상세 합의는 같은 폴더의 `DECISIONS.md`에 저장함. 네 원칙은 사용자 목적·제약을 먼저 확인하고 도구가 설정을 제안하기, 관측·통계·실질적 승패 구분, 비율의 역할 구분, 변수의 역할별 분류임. 구체 통계 설정은 미확정이며, 실제 실험 배포·수집 범위는 아래 Q04에서 후속 합의함.

## Q04 초기 실험 수행 범위 — 사용자 동의

사용자 원문:
> 동의하고 지금까지 같이 논의한걸 깃허브에 저장해놔.

합의: 초기에는 외부 실험 + 도구 내 자연어 설계·분석·설명. 후속에 제한된 내장 비교 시험을 검토할 여지는 남기지만 도입 확정은 아니다. 낮은 입력 장벽을 위해 표 붙여넣기·가이드 양식 등을 검토하고, 집계표와 원자료로 가능한 판단을 구분한다. GitHub에 합의 기록과 참고 자료를 구분해 저장하도록 요청함.

## Q05 결과 입력 방식 — 사용자 동의

질문: 첫 버전부터 ‘자연어·표로 간단히 입력하기’와 ‘파일로 상세 분석하기’를 모두 지원하는 방향에 동의하는가?

사용자 답변:
> 동의

합의:
- 첫 버전에 자연어·표 붙여넣기와 파일 입력을 모두 포함한다.
- 자연어로 읽어낸 군·수치·분자·분모는 구조화해서 사용자에게 확인받는다.
- 간단한 집계로 가능한 비교와 원자료·사전 집단·설계 정보가 필요한 분석을 구분한다. 고객군 정보가 없으면 고객군 차이를 만들어내지 않는다.
- 입력은 쉽게 하되 결론은 확보된 근거와 지원 방법만큼만 제공한다.
- 파일 형식·상세 스키마·처리 위치와 LLM에 전송할 데이터 범위는 아직 미확정이다. 파일 입력 동의는 외부 AI로 원자료 전송하는 동의가 아니다.

저장 상태: 이번 답변은 로컬 인터뷰 기록에 추가했다. 앞서 GitHub에 저장한 Q01~Q04 뒤의 후속 합의이며, 이번 갱신 자체가 원격 저장 완료를 뜻하지 않는다.

## Q06 첫 지원 지표 — 사용자 선택

질문: 성공 여부·비율 중심으로 시작할 것인가, 시간·금액 비교도 첫 버전에 포함할 것인가?

사용자 답변:
> 성공 여부·비율 중심

합의:
- 첫 버전의 주 분석 경로는 고객/참여자별 성공·실패로 정의할 수 있는 결과와 그 비율에 집중한다.
- 예약·구매·정확한 이해 등 상황별로 성공 사건, 분모와 관측 기간을 확인한다.
- 소요 시간·금액·횟수 자체의 평균 등은 첫 지원 분석의 중심에 포함하지 않는다. 이를 임의로 성공/실패로 바꿔 원래 질문에 답했다고 주장하지 않는다.
- 미기록·무응답·관측 미성숙은 자동 실패로 처리하지 않는다.
- 초기 구체 검정·구간·희귀 사건·분모 0 등 처리 방식은 아직 확정 전이다.

## Q07 세그먼트 기준 설정 — 사용자 선택

사용자 답변:
> 세그먼트도 도구가 기준을 추천하되, 사용자가 직접 집단을 지정하거나 추천을 수정할 수 있는 방식으로 진행해

합의:
- 도구는 상황과 실제 사용 가능한 배정 전 속성에 근거해 세그먼트 기준을 추천한다.
- 사용자는 직접 집단을 지정하거나 추천 기준을 수정할 수 있다.
- 추천 기준·사용자 선택·수정 이력과 결과 열람 시점을 남긴다. 존재하지 않는 속성은 만들어내지 않는다.
- 사전 계획한 집단과 결과를 보고 고른 탐색 집단을 구분한다. 사후 선택을 사전 계획으로 바꾸지 않는다.
- 집단별 정보량·결측·중첩과 다중 비교, 직접 효과 차이 검토의 한계를 표시한다. ‘한쪽만 유의’를 집단 차이 증명으로 쓰지 않는다.
- 상세 지원 축 수·집단 수·추천 알고리즘과 통계 방법은 아직 확정하지 않았다.

질문: 채팅만으로 진행하기보다 자연어 대화와 별도의 실험 계획·결과 화면을 함께 제공할 것인가?

사용자 답변:
> 동의

합의:
- 자연어 대화와 구조화된 실험 계획·분석 결과 화면을 함께 제공한다.
- 대화에서 목적·후보·계획을 구체화하고, 별도 화면에서 도구가 이해한 값과 사용자 확인·수정을 가능하게 한다.
- 숫자·집단 기준·제한·판정 근거를 채팅 속에만 남기지 않고 현재 실험의 상태와 연결한다.
- 모바일 배치, 좌우 배치 비율과 상세 화면 설계는 아직 확정하지 않는다.

## Q09 개인 사용과 공유 — 사용자 선택

사용자 답변:
> ‘혼자 설계·분석하고 결과를 공유하는 도구’로 진행해

합의:
- 첫 버전은 개인이 실험을 설계·분석하고 결과를 다른 사람에게 전달하는 도구로 만든다.
- 공동 편집·팀별 권한·다단계 승인 시스템은 초기 범위에서 제외한다.
- 공유할 내용·형식·원자료 포함 여부, 실험 저장·복원, 로그인과 저장 위치는 아직 확정하지 않았다.
- 공유 기능 동의가 고객 원자료의 자동 공개·업로드·외부 AI 전송을 승인하는 것은 아니다.

## Q11~Q20 남은 항목 — 사용자 위임에 따른 권장 방향 선택

사용자는 개별 질문 대신 미라의 권장 방향으로 진행하도록 위임했다. 다음 항목은 직접 답변으로 꾸미지 않고 위임 결정으로 기록한다.

- Q11: 시작 경로 — 세 가지 진입, 하나의 실험 기록
- Q12: 첫 파일 지원 — CSV 우선, 표 붙여넣기 병행
- Q13: 저장·로그인 — 제품 가입 없이 시작, 명시적 프로젝트 파일 저장
- Q14: 공유 — 읽기용 HTML 보고서와 인쇄 PDF
- Q15: 결과 설명 — 결론 먼저, 근거를 펼쳐보기
- Q16: 정보 부족과 오류 — 안내는 계속, 근거 없는 판정은 중단
- Q17: 초기 통계 지원 — 검증 가능한 좁은 범위
- Q18: 변경·재현 — 계획과 결과를 버전으로 연결
- Q19: LLM 연결 — 교체 가능한 설명 계층과 고장 시 대안
- Q20: 개발·검증 — UI와 통계를 따로 시험하고 합치기

상세 정책과 수용 기준은 같은 폴더의 PRD_BASELINE_v02.md를 우선한다. 기존 HTML은 초기 참고 초안이다. 통계 알고리즘·전송/저장 구현·키 보관·성능·공급자는 기술 명세와 검증을 거쳐야 하며, 비용·실제 고객 데이터 전송·공개 배포는 자동 승인되지 않는다.

설계 원칙 제안(사용자 확정 전):
- 자연어가 통계 계산과 실험 타당성을 대신하지 않게 한다.
- 실제 데이터에서 계산한 결과를 LLM이 설명하며, 필요한 정보가 부족하면 질문한다.
- 두 안을 언급했다는 이유만으로 무작위 A/B 실험으로 취급하지 않는다.
