# PRD 합의 기록 — 자연어 기반 A/B 테스트 안내

이 문서는 사용자와의 PRD 문답에서 합의한 흐름과 보존 요청한 네 설계 원칙을 기록한다. 기존 HTML PRD는 앞서 만든 참고 초안이며, 이 합의를 모두 반영한 승인 PRD로 취급하지 않는다. 초기 MVP는 외부 실험 결과를 받아 도구 안에서 자연어 설계·분석·설명을 제공하기로 합의했다. 이후 Q10의 동의와 나머지 항목 위임으로 초기 제품 정책을 구체화했으며 BASELINE.md를 최신 기준안으로 둔다. 구체 통계 알고리즘·상세 파일 계약·저장/보안 구현과 후속 내장 시험 도입은 별도 명세·검증 사항이다.

## 1. 사용자가 합의한 기본 흐름

**상황 설명 → 목적 확인 → A/B 후보 제안 → 지표·배정·판정 계획 추천 → 사용자 확인 → 결과 분석과 설명**

- 비교 후보와 통계 용어를 몰라도 상황 설명으로 시작할 수 있다.
- 데이터가 없을 때는 방향과 시험 계획을 제안한다. 실제 실험 결과나 승자를 만들어내지 않는다.
- LLM은 질문 구체화·후보·계획 제안·결과 설명을 담당하고, 실제 판정은 데이터와 검증된 계산에 연결한다.
- 결과 분석과 설명의 앞에는 실제 실험 수행과 결과 확보가 필요하다. 첫 버전은 외부에서 실험하고 결과를 가져오며, 내장 실험 배포·수집은 포함하지 않기로 합의했다.
- 우선순위는 결과와 승패·집단 차이 이해 → 설계 확신 → 다음 행동 결정 지원이다.

## 2. 보존 요청한 이전 답변 1~4의 설계 원칙

### 원칙 1. 사용자가 통계 설정을 처음부터 정하게 하지 않는다

사용자에게 먼저 물어볼 것은 통계 용어가 아니라 목적과 현실 조건이다.

| 사용자에게 확인할 것 | 도구가 제안할 것 |
|---|---|
| 무엇을 더 좋게 만들고 싶은가? | 주지표와 비교 후보 |
| 누구에게, 어디에서 보여줄 것인가? | 실험 대상과 배정 방법 |
| 어떤 결과를 기록할 수 있는가? | 측정 방법과 분자·분모 |
| 어떤 부작용은 피해야 하는가? | 보호 지표와 허용 조건 |
| 어느 정도 차이면 바꿀 만한가? | 실질적 개선 기준과 표본 계획 |

도구가 초안을 만들고 사용자는 이해할 수 있는 말로 확인·수정한다. 자세한 통계 설정은 필요할 때 펼쳐본다. 사용자의 확인만으로 잘못된 통계 설계가 유효해지지는 않는다.

### 원칙 2. 위너 기준은 ‘무엇이 좋다는 뜻인지’부터 정한다

지하철 도착 문구라면 정확한 이해, 빠른 파악, 낮은 혼동·불안은 서로 다른 목적일 수 있다. 목적을 확인하고 지표를 추천한다. 정확한 이해가 목적이면 이해도 질문의 정확 응답 비율을 주지표 후보로 제안할 수 있지만, 이것은 상황에 따른 제안이지 이미 확정된 주지표가 아니다.

위너를 하나의 성공 배지로 압축하지 않는다.
1. 관측 결과: 어느 안의 수치가 더 좋은가?
2. 통계 판단: 차이를 뒷받침할 근거가 충분한가?
3. 실질적 판단: 바꿀 만한 차이이며 보호 조건에 문제가 없는가?

주지표와 판정 계획은 결과 확인 전에 정하고 변경 이력을 남긴다. 결과를 본 뒤 유리한 지표를 골라 승자를 만들지 않는다. 충분한 근거가 없으면 승패를 보류할 수 있어야 한다.

### 원칙 3. ‘비율’은 구분해서 다룬다

| 비율의 종류 | 처리 원칙 |
|---|---|
| A/B 배정 비율 | 비용·위험 등 조건이 비슷하면 균등 배정을 초안으로 제안. 특정 안의 노출을 제한해야 하는 사유 확인 |
| 지표의 분자·분모 | 목적에 맞게 제안하고 실제 수집 가능한지 확인. 누구 전체에서 무엇이 발생한 비율인지 명시 |
| 현재 수준과 목표 개선 폭 | 기존 데이터가 있으면 사용. 없으면 미확인으로 두고 예비 측정이나 가정별 계획 제안 |
| 통계적 오류 기준 | 검증된 기본 설정의 의미를 설명하고 위험·설계에 맞게 확정. 결과를 보고 기준을 느슨하게 바꾸지 않음 |

초보 사용자에게 배정 숫자부터 요구하지 않고 ‘한 안이 잘못됐을 때 위험이나 추가 비용이 있는가?’처럼 의미 있는 조건을 질문한다. 무응답·누락을 임의로 분모에서 빼거나 실패로 처리하지 않는다. 누락 처리는 측정 계획의 일부다.

### 원칙 4. 다양한 변수는 역할별로 정리한다

| 역할 | 지하철 문구 예시 | 처리 방향 |
|---|---|---|
| 바꿀 것 | 문구 표현 | A/B 차이로 명시 |
| 같게 유지할 것 | 실제 도착 정보·글자 크기·화면 배치 | 문구 효과를 보려면 가능한 한 동일하게 유지 |
| 배정에서 고려할 것 | 장소·시간대·이용 경험 | 무작위 배정, 필요하면 사전 블록 설계 검토 |
| 나눠 볼 것 | 사전 정의한 이용 경험 집단 | 이유와 정보량이 있을 때 집단별 효과 검토 |
| 측정할 결과 | 정확한 이해·소요 시간·혼동 | 주지표·진단·보호 역할 구분 |

모든 변수를 완벽히 통제하거나 AI가 자동 보정할 수 있다고 약속하지 않는다. 중요한 요인을 찾아 확인하고 남은 한계를 기록한다. 같은 사람이 A/B를 모두 보는 경우에는 순서·학습·반복 측정을 고려하며 독립 두 집단 실험으로 자동 처리하지 않는다. 실제 운영 안내를 임의로 바꾼다는 뜻도 아니다.

## 3. 사용자 합의 — 첫 버전의 실험 수행과 수집 범위

질문: 도구 안에서 간단한 A/B 비교 화면·설문을 만들고 결과까지 수집할 것인가, 아니면 외부에서 실험하고 도구는 설계·분석·설명을 맡을 것인가?

사용자가 권장안에 동의함. 확정한 초기 방향:
- 초기 MVP는 외부 실험 + 도구 내 자연어 설계·분석·설명으로 시작한다.
- 결과 입력은 고객 원자료 CSV만 강요하지 않고 지원 가능한 표 붙여넣기·가이드 양식을 검토한다. 집계표로 가능한 판단과 원자료·설계 정보가 필요한 판단을 구분한다.
- 일상 신규 실험의 진입 장벽은 실제 사용 과제로 검증한다. 외부 도구와 파일 준비 부담이 크면 제한된 내장 비교 시험을 후속 우선순위로 검토한다.
- 최종적으로 외부 결과와 제한된 내장 비교 시험을 함께 지원할 여지는 남기되, 참여자 모집·동의·안정 배정·중복·탈락·개인정보·이벤트 수집까지 첫 버전에 모두 넣지는 않는다.
- 사용자는 “동의하고 지금까지 같이 논의한걸 깃허브에 저장해놔.”라고 답했다. 초기 범위는 합의됐으나 내장 시험을 반드시 구현한다는 승인이나 플랫폼·통계·저장 기술의 확정은 아니다.

## 4. 이후 문답에서 추가 합의한 사항 — Q05~Q10

- 입력: 첫 버전에 자연어·표 붙여넣기와 파일 입력을 모두 포함한다. 추출한 군·수치·분모를 확인받고, 집계표와 원자료로 가능한 분석을 구분한다.
- 지표: 초기 주 분석은 성공 여부·비율 중심이다. 시간·금액의 평균 등은 이 지원 범위에 억지로 넣지 않는다. 누락과 미성숙은 자동 실패가 아니다.
- 세그먼트: 도구가 실제 사용 가능한 속성에 근거해 추천하고, 사용자는 직접 지정하거나 추천을 수정할 수 있다. 사전 계획과 사후 탐색을 구분한다.
- 화면: 자연어 대화와 별도의 구조화된 실험 계획·결과 화면을 함께 제공한다. 대화 속에 숫자와 설정을 묻어두지 않고 확인·수정할 수 있게 한다.
- 사용 방식(Q09): 첫 버전은 개인이 설계·분석하고 결과를 공유한다. 공동 편집·팀별 권한·다단계 승인 시스템은 제외한다. 공유 형식과 원자료 포함 여부는 미확정이다.
- LLM 경계(Q10): 고객별 원자료는 기기에서 검증·계산하고 LLM에는 추천·설명에 필요한 최소 정보만 전달하기로 동의했다.
- Q11~Q20은 사용자 위임으로 권장 방향을 선택했다. 입력·저장·공유·화면·오류·초기 통계 지원·변경·LLM·검증의 상세 기본 정책은 BASELINE.md를 우선한다. 정확한 계산·보안 구현과 성능 등은 별도 명세·시험이 필요하다.

이 후속 합의는 로컬 기록에 추가했다. 앞서 원격 저장한 Q01~Q04와 구분하며, 이후 별도 반영 전에는 GitHub가 갱신됐다고 말하지 않는다.
