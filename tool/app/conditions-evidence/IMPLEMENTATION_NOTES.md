# Condition record implementation and verification boundaries

- Core conditions: randomized assignment, independent units, mature per-person observation, fixed stopping. Each visible select has yes/no/unknown. Unknown is the default. Only exact yes projects to the existing engine boolean; no hidden checkboxes exist. Engine math and guards are unchanged.
- Segment prespecification is separate. Its no/unknown permits valid overall inference when the four core conditions are yes, while segment inference remains exploratory/blocked under existing engine rules.
- Evidence is optional user text, max 1,000 UTF-16 code units per condition. It neither promotes a state nor verifies execution. It is stored verbatim in local JSON, rendered escaped in local method details, excluded from public HTML/PDF and minimal explanation facts. No automatic model request was introduced.
- Storage schema7 duplicates the old plan booleans only for compatibility. Read/write share normalization; conflicts, unsupported declarations, invalid states/origins and overlong evidence are rejected before applying a restore. Existing schema2–6 true is retained as an explicit legacy user confirmation with empty evidence; false becomes unknown, never known denial. No evidence is invented. Editing that record changes its origin to user_statement, not independent verification.
- CSV, text/format changes and design-to-input reset conditions/evidence. Demo yes values are labeled synthetic assumptions. R05 plan confirmation does not alter analysis conditions. Condition/evidence edits use existing input epoch invalidation for result, numeric confirmation, LLM consent, share approval and print DOM.
- Existing video bytes and dialog implementation are unchanged. The video depicts earlier checkbox assumptions; no new conditions/design tutorial was added. Actual playback/close/Escape tests snapshot every select and evidence value along with state, URL and time origin. Existing 84-check help/interface suite is rerun independently.

## Initial failures and corrections

`evidence/r06-initial/result.json` and exact logs preserve the first complete integration run. The new condition suite and its browser workflow passed on that run. Three old tests failed: lineage expected output schema6; browser meta helper called checkbox-only set_checked on a now-visible select; mechanical action conversion produced invalid Python in one Locator.uncheck site of the help suite. These were **test-adaptation fixes**, not an engine change or an application gate workaround. The tests now use real visible select_option and real checkbox actions according to element type. The earlier isolated schema expectation failure is in `schema-expectation.log`. No initial failure is relabeled a successful historical run. Later source and extracted results are distinct records.

The next complete run passed the adapted tests but hit the existing 5-second large-file source-badge assertion on 50,000 rows. Its exact failure and result are preserved in `evidence/r06-readwait-initial/`. Diagnostic readback showed the file text and CSV state had arrived; no file-read application code was changed. The assertion now waits on the same visible state with a bounded 60-second timeout. This is a test wait change, not a general performance fix. A final source review also removed the obsolete no-op assignment to `select.checked` when no segment data exists; condition projection had already used only select.value. This application cleanup does not change engine math or grant inference.

The first baseline-manifest command inherited a system TEMP value despite the supplied runtime description. Its one generated JSON was immediately moved into active-profile scratch and the original removed. All subsequent test/package commands explicitly set TMPDIR, TEMP and TMP to active-profile scratch. No old Downloads app or e-book was read or changed.

## Evidence scope

`conditions_verification.json` and `conditions-evidence/` contain actual synthetic browser/download/PDF artifacts; `tests/conditions_smoke.cjs` runs the unchanged engine through the projected conditions. `verification.json` summarizes actual current logs; original narrative/model/full video-decode records remain labeled historical, not rerun. Initial control hashes are recorded in `BASELINE_CONTROLS.json` against the clean base 9fb9873aeafa342425857f202134296f1eca98a8. Parent owns its separately pinned Git backup and root summary/publishing.

The tested browser is actual Windows Chrome, not all browsers/devices. Human observations and live model calls are zero. No claim of independent experiment validation, statistical scope expansion, full accessibility/security certification, or real business outcome is made.
