# v0.4 추가 검증 결과 — 상태·저장 결함 확인

## 판정

**계산·설명 자동 검사는 통과했으나, 입력·인쇄·저장 상태의 정확성에 우선 수정할 문제가 있다.** 기존 정상 경로 검사의 통과를 실사용 전체 검증 완료로 확대하지 않는다.

이번에는 앱·기존 테스트·배포 ZIP을 수정하지 않았다. 별도 감사 폴더의 테스트와 증거만 만들었다. 실제 고객자료·credentials를 읽지 않았고 실제 모델 호출을 하지 않았다.

## 검증 구성

- 실제 Chrome의 새 컨텍스트에서 합성 입력으로 E01~E07을 수행했다. 사용자의 기존 탭과 데이터는 건드리지 않았다.
- E02와 E03은 **실제 해시/파일 읽기의 완료 시점만 지연**했다. 실제 해시와 파일 바이트를 바꾸거나 가짜 통계 결과를 만들지 않았다. 이는 비동기 순서 결함의 결정적 재현이며 발생 빈도·평균 성능을 측정한 것이 아니다.
- E06은 명시적으로 주입한 HTTP 503이다. 실제 모델의 성공·실패로 세지 않는다.
- 실제 engine→narrative 경로의 고정 합성 입력 1,728건과 자동 assertion 15,441건을 실행했다. A/B 및 집단 교환과 연관 검사가 포함되므로 서로 독립인 실험 15,441건이라는 뜻이 아니다.
- 별도 순수 함수/스키마 검증으로 모델 facts·공유 제외·저장/복원 조건을 확인했다. 이 두 검토 스크립트는 부모가 다시 실행해 종료 코드 0을 확인했다.

## 우선 수정할 네 가지

### W01 — 나중에 입력한 표가 먼저 선택한 파일에 덮인다

- 우선도: 높음. 입력 의도 보존과 잘못된 자료 사용 위험.
- 재현: E03. CSV 파일의 실제 읽기가 끝나기 전에 새 표를 붙여넣고, 앞선 파일 읽기를 완료시킨다.
- 관측: 새 표가 사라지고 앞선 CSV 내용으로 바뀌며 출처도 사용자 CSV로 표시된다. 실제 입력은 서로 다른 합성 값으로 구분했다.
- 원인 위치: app.js의 csv-file change handler는 fileTicket을 파일 선택끼리만 비교한다. 텍스트 편집 등 다른 입력 경로가 앞선 파일 작업을 무효화하지 않는다.
- 기대: 최신 사용자 입력을 유지하거나, 완료된 이전 파일을 적용할지 명시적으로 묻는다. 늦게 끝났다는 이유로 최신 입력을 덮어쓰지 않는다.
- 권장 수정: 파일·텍스트·형식·복원·새 실험을 공통 입력 작업 번호로 묶고 모든 await 뒤 소유권을 확인한다. 파일 선택 즉시 읽는 중 상태와 이전 작업의 무효화를 반영한다.
- 한계: 완료 순서를 통제한 재현이다. 실제 사용자에게 얼마나 자주 발생하는지는 측정하지 않았다.

### W02 — 결과 무효화 뒤에도 인쇄용 옛 보고서가 남는다

- 우선도: 높음. 보고서 최신성 위험이며 접근권한 취약점으로 분류하지 않는다.
- 재현: E01. 기존 보고서를 확인하고 앱의 인쇄 버튼으로 인쇄용 DOM을 만든 뒤, 입력 화면에서 분석 대상을 변경한다. 앱 인쇄 버튼을 다시 누르지 않고 브라우저 인쇄 파이프라인으로 PDF를 만든다.
- 관측: 결과 이동은 차단되고 공유 확인도 해제됐지만 #print-area에 옛 대상·옛 결정이 남는다. 실제 PDF에서도 OLD 표식이 확인되고 NEW 표식은 없다.
- 증거: e2e/stale_print_after_edit.pdf, e2e/PRINT_TEXT_PROOF.json. 이는 DOM 문자열 확인만이 아니라 실제 PDF 텍스트로 확인했다.
- 원인 위치: markChanged와 판단·공유 범위 변경은 인쇄용 DOM을 지우지 않는다. 인쇄 버튼을 누를 때만 #print-area를 갱신한다. 인쇄 CSS는 작업 화면을 숨기고 이 영역을 출력한다.
- 기대: 현재 결과·공유 확인과 일치하지 않는 옛 보고서를 인쇄하지 않는다.
- 권장 수정: 입력·판단·공유 범위 변경 시 인쇄 스냅샷을 폐기한다. beforeprint에서도 현재 확인된 결과·회차·공유 범위인지 검사하고, 아니면 자료가 아닌 안내만 출력한다.
- 경계: 옛 보고서에는 옛 회차·원천 표시가 있다. 이를 새 계산 결과를 위조한 것으로 표현하지 않는다. 문제는 최신 UI 상태와 인쇄 상태의 불일치다.

### W03 — 해시 계산 중 입력을 바꾸면 확인 버튼이 잠긴다

- 우선도: 중간. 정상 작업을 계속할 수 없게 됨.
- 재현: E02. 실제 SHA-256 결과의 반환을 지연한 상태에서 새 표로 바꾼 뒤 해시 완료를 허용한다.
- 관측: Worker busy는 false인데 ‘데이터 확인하기’ 버튼은 비활성으로 남는다. 표는 편집할 수 있지만 확인 작업을 다시 시작할 수 없다.
- 원인 위치: prepare는 Worker 전의 해시 단계부터 버튼을 잠근다. markChanged는 Worker busy일 때만 버튼을 풀고, 오래된 prepare의 finally는 회차가 바뀌면 버튼을 풀지 않는다.
- 기대: 취소된 해시 작업 때문에 재시도가 막히지 않는다. 동시에 옛 작업의 finally가 새 작업 버튼 상태를 잘못 풀지도 않아야 한다.
- 권장 수정: 해시·읽기·파싱을 포함하는 입력 작업 상태를 하나로 관리하고, 현재 작업만 버튼 상태를 소유하게 한다.
- 한계: 실제 crypto 계산을 지연한 순서 재현이다. 사용자 기기에서의 보편적 발생 빈도는 확인하지 않았다.

### W04 — 앱이 저장한 프로젝트를 앱이 다시 열지 못하는 경우가 있다

- 우선도: 중간. 저장·복원 계약 불일치.
- 중복을 합친 증거: E04·E07, static PC-01.

|입력|저장|복원|범위|
|---|---|---|---|
|201자 집단명, 2집단·4셀·군별 200명|성공|집계 유효성 오류|인원·집단 수는 추론 지원 범위 안이며 파서에는 길이 오류가 없음|
|7집단·14셀|성공|파일 형식 오류|집단 추론 지원 밖. 그 자체가 통계 오류라는 뜻 아님|
|군별 200001명|성공|집계 유효성 오류|추론 상한 밖. 역시 잘못된 p값을 만들었다는 뜻 아님|

- 원인 위치: prepare 및 projectObject/저장 경로와 restoreProject의 cells 길이·segment 길이·total 제한이 다르다.
- 기대: 저장을 허용한 파일은 다시 읽거나, 저장 전에 해당 형식으로 보존할 수 없는 이유를 명확히 안내한다.
- 권장 수정: 입력/저장/복원용 공통 스키마를 두고 분석 지원 범위와 저장 가능 범위를 분리한다. 저장을 위해 추론 상한을 임의로 높이거나 오류 행을 버리지 않는다.
- 201자 사례는 부모가 실제 브라우저 다운로드·복원으로 재확인했다. 다른 정적 사례의 VM 실행과 구분해 기록했다.

## 설명 보완 — 낮은 우선도, 수학 결함과 분리

- N-01: 사전성 미확인과 집단 결측이 동시에 있을 때 설명 카드가 탐색 지위만 먼저 안내한다. 결측 경고는 엔진 issues에 남으므로 앱 전체에서 숨겨진다고 단정하지 않는다. 여러 제한을 함께 설명하면 좋다.
- N-02: 한 집단의 A 분모가 0인 확정 원인을 포괄적인 GROUP_UNSUPPORTED 안내로 대체한다. 잘못된 승자를 만들지는 않지만 빈 군을 정확히 특정하는 편이 낫다.
- N-03: 실제 invalid 결과를 직접 설명 API에 넘기면 interaction 안내가 기술 통계를 사용하라고 말할 수 있다. 정상 UI는 prepare 오류에서 분석을 막으므로 주된 사용자 경로 결함이 아니라 방어적 API 문구 보완이다.

각 재현 입력·기대·관측 문장은 narrative/REPORT_ko.md와 narrative/narrative_results.json에 있다.

## 개인정보·원천 기록의 추가 한계

- PC-02: 서버 issues는 알려진 코드 허용목록이 아니라 코드 모양 정규식만 검사한다. 개인정보처럼 생긴 합성 문자열도 순수 validator를 통과했다. 정상 UI는 엔진 코드를 만들므로 **이번에 정상 UI의 개인정보 유출이나 실제 모델 전송이 재현된 것은 아니다.** raw_data_sent:false를 임의의 모든 클라이언트 입력에 대한 익명성 인증으로 해석하면 안 된다. 허용목록 검증과 보증 문구의 범위 명시를 권장한다.
- PC-03: 저장한 source_digest를 복원하지 않고 집계 CSV를 재준비하면 현재 입력 해시로 바뀐다. 원자료 재검증은 원래 보장하지 않으므로 인증 우회로 분류하지 않는다. 원천 해시와 복원 집계 해시를 별도 계보로 보관하면 추적성이 좋아진다.

## 확인한 보호·정상 동작

- 잘못된 JSON 프로젝트를 읽어도 기존 결과는 보존됐다(E05).
- 입력 변경·재분석 뒤 늦게 도착한 이전 설명 요청의 실패가 새 결과·상태를 덮지 않았다(E06, 주입 시험).
- 검토한 정상 facts 생성 경로에서 정책·대상·목적·원래 집단명이 모델 payload에 섞이지 않았다.
- 집단 공유 제외 보고서 문자열에 검사한 집단명·집단 설명·집단 p값이 남지 않았다. 비교 가족의 G1/G2 식별자는 상세 수치와 구분했다.
- 경고된 자유 서술 공유와 HTML 이스케이프는 정상 동작이었다.
- 1,728개 고정 합성 입력과 15,441개 자동 검사의 범위에서는 승자 반전·잘못된 유의성/보정 판정 설명·교환 불변성 위반을 발견하지 못했다. 대규모 확률 정밀도나 모든 통계 상황·사용성을 인증한 것이 아니다.

## 수정 순서와 회귀 수용 기준

1. **입력 작업 소유권**: W01·W03. 파일 읽기·해시·Worker 단계 각각에서 새 편집/복원/형식 변경을 끼워 넣어 최신 입력 유지와 재시도 가능성을 확인한다.
2. **인쇄 상태 최신성**: W02. 기존 보고서 생성 뒤 입력·결정·공유 범위를 바꾸고 브라우저 인쇄/PDF를 확인한다. 현재 확인되지 않은 옛 보고서를 내보내지 않아야 한다.
3. **저장 스키마 통일**: W04. 저장 허용 경계의 이름 길이·셀 수·인원·파일 크기에서 저장→복원→재분석을 검사한다. 미지원 입력은 조용히 잘라 저장하지 않는다.
4. 복합 제한 설명·서버 코드 허용목록·해시 계보를 보완한다.

새 기능이나 입력 열 매핑보다 위 상태·저장 문제를 먼저 고치는 것을 권장한다. 이번 요청은 검증으로 수행했으며 **수정 완료를 주장하지 않는다.**
