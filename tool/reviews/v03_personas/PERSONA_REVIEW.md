# 작업실 v0.3 가상 페르소나 검토

## 결론

외관을 더 꾸미는 것보다 **실험 맥락을 잃지 않는 결과, 고객군별 판단 이유, 실제 자료의 입력 부담**을 먼저 개선하는 것이 적합하다. 지금은 지원 조건 안에서 계산과 보고서를 만드는 앱으로 작동하지만, 통계를 잘 모르는 CRM 실무자가 혼자 판단까지 마치는 경험은 더 보완할 여지가 있다. 이는 현재 화면·코드와 합성 과업을 바탕으로 한 제품 평가 가설이며 실제 사용자 성과 측정이 아니다.

앱·계산 엔진·기존 ZIP은 수정하지 않았다. 검토 자료만 별도 폴더에 저장했다.

## 검토 방법과 한계

- 대상: AB_Test_Workspace_v03의 실제 입력·결과·판단 정리 화면과 app.js.
- 실제 Chrome의 독립된 새 브라우저 컨텍스트에서 합성 자료로 과업을 수행했다. 사용자의 기존 탭과 입력은 건드리지 않았다.
- 관찰은 OBSERVATIONS.json의 O01~O07에 기록했다. 기존 화면 캡처도 직접 열어 위계와 문구를 확인했다.
- 실제 인터뷰·사람의 사용성 시험·CRM 테넌트 사용시험은 아니다. 성공률·소요 시간·매출 개선·지불 의사 점수를 만들지 않았다.
- 모델에 자료를 보내는 요청을 하지 않았다. 이번 평가에서 LLM POST는 없었다.
- 기존 대비 검토를 재사용했으며 이번에 색을 바꾸거나 대비를 다시 계산하지 않았다. 색은 이번 핵심 문제로 선정하지 않았다.

## 이미 잘 갖춰진 부분 — 유지

- 실제 입력 검증·통계 계산과 LLM 설명이 분리되어 있다.
- 원자료를 브라우저에서 처리하고 모델 전송에 별도 확인을 둔다.
- 전체·집단·직접 효과 차이, 원래 p값·조정 p값·명목 구간을 실제로 제공한다. 집단 분석이 없다고 평가하지 않는다.
- 추론 조건이 미확인되면 판정을 제한하고, 자료·조건 변경 시 이전 결과를 무효화한다.
- 목적·정책 메모와 자료 없는 계획 저장이 가능하다. 설계 진입이 완전히 없다고 평가하지 않는다.
- 보고서에 목적·성공 사건·관측 기간·판단·재검토 조건을 포함하며 집단 상세는 기본 제외한다. 보고서에 맥락이 전혀 없다고 평가하지 않는다.
- 합성 자료는 출처가 표시되며 프로젝트 복원에도 그 구분을 유지한다.

## 관찰 기반 개선점

### F01. 입력한 A/B 정책이 결과와 보고서에 이어지지 않는다 — 최우선

- 관련 역할: CRM-01, LEAD-01, ANL-01.
- 근거 O05: 정책 필드에 서로 다른 설명을 입력한 뒤 분석·공유 화면을 확인했다. 해당 정책 문자열은 결과와 집단 포함 보고서 모두에서 나타나지 않았다. app.js에서 정책은 프로젝트 저장에 있지만 reportHTML의 정책 설명 렌더에는 연결되어 있지 않다.
- 영향 가설: 보고서에 A/B 코드와 비율은 있어도 각 코드가 어떤 메시지·혜택·시점을 뜻하는지 따로 설명해야 한다. 사용자가 목적 문장에 직접 적으면 보완할 수 있지만 자동 인계가 되지는 않는다.
- 제안: 결과와 보고서에 A/B 설명, 성공 사건, 관측 기간, 대상 범위를 짧은 ‘무엇을 비교했나요’ 영역으로 연결한다. 기존 필드 재사용부터 시작한다. 실험별 대상 입력은 전사 CRM 관리로 확장하지 않는다.
- 수용 기준: 정책 설명을 다르게 입력하면 결과·HTML·PDF의 동일한 A/B와 정확하게 연결된다. 미기록이면 추정하지 않고 ‘설명 미기록’을 표시한다. 내보낼 텍스트는 이스케이프하며 민감정보 검토를 안내한다.
- 비용 판단: 기존 정책 필드의 연결은 낮음. 대상 구조화는 중간.

### F02. 보류라는 상태는 있으나 이번 결과의 보류 이유가 약하다 — 최우선

- 관련 역할: CRM-01, NEW-01, LEAD-01.
- 근거 O04: 전체 13.00%와 15.00%, 차이 +2.00pp, 조정 p값 0.44150과 승패 보류를 제공한다. 신규 집단에서는 명목 구간이 +0.90pp~+9.12pp, 원 p값 0.02145이지만 조정 p값 0.08581로 보류다. 실제 해석 영역은 ‘보류는 동등성·안전의 증명이 아니다’라는 공통 안내 중심이다.
- 영향 가설: 사용자가 ‘비율이 더 높은데 왜 못 고르는가’, ‘구간과 판정이 왜 달라 보이는가’를 스스로 해독해야 한다.
- 제안: 로컬 계산 결과로 전체·집단·직접 차이의 한 문장 이유를 만든다. 기본 레이어에는 ‘성공 비율 차이’, ‘판정’, ‘이번 판정 이유’를 두고 위험차·명목 구간·p값은 근거 레이어로 연결한다. AI가 계산하거나 숫자를 새로 만들게 하지 않는다.
- 문구 제안: ‘신규 고객에서는 B의 완료율이 높게 관측됐지만, 여러 비교를 함께 고려한 기준에서는 승패를 정할 근거가 부족해요.’
- 경계: 명목 Wilson/Newcombe 구간을 Holm 동시 구간처럼 설명하지 않는다. Fisher와 구간이 완전히 쌍대라고 쓰지 않는다. 보류를 효과 없음·안전·동등으로 바꾸지 않는다.
- 수용 기준: 전체 보류, 보정 후 보류, 설계 미확인, 직접 집단 차이 미지원의 이유가 서로 다르게 표시된다. 실제 값을 쓰며 원래 엔진 판정과 일치한다. 적용 승인은 별개로 남는다.
- 비용 판단: 중간.

### F03. 실무 자료를 계약 헤더로 바꾸는 일이 앱 밖에 남아 있다 — 최우선

- 관련 역할: CRM-01, NEW-01.
- 근거 O03: ‘안,완료수,배정수,고객군’ 헤더의 합성 표는 UNKNOWN_HEADER와 MISSING_HEADER 오류를 반환하고 분석을 차단했다. 오류는 영문 문장과 코드로 나타난다. 잘못된 의미를 자동 추정하지 않는 차단은 적절하나 열 매핑 UI는 없다.
- 영향 가설: 정확한 표를 갖고 있어도 열 이름·A/B 값·이항 결과를 사람이 외부에서 다시 정리해야 한다.
- 제안: 로컬 미리보기 → 열 연결 → A/B 값 연결 → 분자·분모 의미 확인 → 검증 순서. 열 이름 후보 추천은 가능하되 의미를 확정하거나 누락을 0으로 채우지 않는다. A/B별 성공·분모를 직접 입력하는 작은 표와 계약 CSV 다운로드를 빠른 경로로 둔다.
- 문구 전→후: ‘UNKNOWN_HEADER / exact English headers are required’ → ‘전체 인원을 뜻하는 열을 연결해 주세요. 발송 수·도달 수·배정 수는 같은 분모가 아닐 수 있어요.’ 실제 원인이 분모 부족인지 먼저 분류한다.
- 수용 기준: 한글 헤더 자료를 사용자가 명시적으로 매핑하면 현재 표준 계약과 동일한 검증 결과를 얻는다. 모호한 분모·결과는 확인 전 판정하지 않는다. 원자료의 외부 전송 없이 수행한다.
- 비용 판단: 중간.

### F04. 세그먼트 계산은 있으나 대상 정의와 사전/탐색 관리가 데이터 열·체크에 의존한다 — 후속 핵심

- 관련 역할: CRM-01, ANL-01.
- 근거 O07 및 소스: CSV segment와 사전성 체크로 집단을 지정·변경할 수 있다. 전용 속성 선택·집단 정의·기준시점·변경 경위 화면은 없다. 현재 회차와 결과 무효화는 있지만 그것이 사전등록 인증이나 의미 있는 집단 변경 이력을 뜻하지는 않는다.
- 제안: 실제 존재하는 배정 전 속성만 후보로 보여주고, 두 집단의 정의·분모·결측을 확인한다. 결과 열람 후 새 기준을 고르면 탐색을 기본값으로 하되, 외부에 이미 고정된 사전 계획을 가져오는 경우에는 그 근거를 별도로 기록한다. 단순 오탈자 수정을 새로운 사후 분석과 동일시하지 않는다.
- 경계: 효과가 크게 보이는 집단을 자동 추천해 사전 분석으로 표시하지 않는다. 한 집단 유의/다른 집단 비유의로 직접 차이를 확정하지 않는다. 지원 범위를 넘는 집단 수를 조용히 분석하거나 제외하지 않는다.
- 수용 기준: 정의·시점·결측·사전/탐색 지위가 계획·결과·보고서에 일치한다. 공유 제외를 선택하면 해당 상세 정보는 실제 파일에서도 제외된다.
- 비용 판단: 중간~높음. 결과 요약에서 집단을 앞에 배치하는 F02와 함께 작은 범위부터 시작한다.

### F05. ‘모른다’는 조건을 사용자가 해결할 안내가 부족하다 — 후속

- 근거 O06: 무작위 배정 체크를 해제하면 ‘판정 미실행’으로 제한된다. 차단은 정상이며 실패로 평가하지 않는다. 다만 구체적으로 어떤 기록을 확인해야 하는지는 공통 규칙 설명 중심이다.
- 제안: 조건마다 ‘확인함/모름/해당하지 않음’, 확인할 기록 예시, 가능한 기술 통계와 불가능한 주장을 보여준다. 예를 들어 무작위는 배정 로직·추출 기록, 관측 완료는 개인별 기산점·종료일을 안내한다. 출처를 확인한 사실과 사용자 진술을 구분한다.
- 수용 기준: 미확인 상태에서 추론을 풀지 않고도 사용자가 필요한 다음 확인을 알아볼 수 있다. 체크만으로 실제 무작위성·독립성을 인증하지 않는다.

### F06. 결과 없는 사람의 시작 경로는 메모 수준에 머문다 — 이후 단계

- 근거 O01·O02: 목적과 정책을 적고 자료 없는 프로젝트를 저장할 수 있으며 규칙 체크리스트도 있다. 그러나 현재 첫 화면은 ‘실험 결과를 가져와 주세요’이고 상황에 맞춘 후보·지표·설계 초안은 생성하지 않는다.
- 제안: 동일한 실험 기록 안에서 ‘결과 분석하기 / 실험 준비하기’ 진입을 나눈다. 목적·현재 정책·변경할 한 요소·성공 사건·관측 기회·배정·사전 집단을 확인해 초안을 만든다. 자유 자연어 LLM 제안은 별도 계약·동의 후 붙인다.
- 경계: 아직 없는 표본 수 계산·연속형 분석·CRM 배포 기능을 작동하는 것처럼 표시하지 않는다. 현재 사용자의 결과 이해 우선순위를 고려해 F01~F03보다 먼저 큰 채팅 기능을 만들지는 않는다.

## 권장 개발 순서

1. **다음 작은 판:** F01 실험 맥락 인계 + F02 결과별 이유·전체/집단/직접 차이 요약.
2. **그다음 판:** F03 로컬 열 매핑·간단 표 입력 + F05 확인할 기록 안내.
3. **이어서:** F04 집단 정의·변경 경위와 F06 상황 기반 설계 초안을 동일 실험 기록으로 연결.

F04의 중요도를 낮춘다는 뜻이 아니다. 집단별 결과를 쉽게 읽는 부분은 첫 판 F02에 포함하고, 구조화된 정의·이력은 별도 입력 계약과 함께 확장한다.

## 실제 사람에게 확인할 과업 — 제안, 미실행

- 주 사용자에게 서로 다른 A/B 정책과 익숙하지 않은 열 이름의 표를 주고 무엇을 어디에 연결해야 하는지 관찰한다.
- 전체 보류·집단의 명목 구간과 보정 판정이 다른 결과를 보고 가능한 주장과 불가능한 주장을 자기 말로 설명하게 한다.
- 결과 수신자에게 보고서만 주고 A/B 정책·지표·대상·현재 선택·미확인 조건을 찾아 설명하게 한다.
- 검토자에게 결과 열람 뒤 바뀐 집단 정의를 주고 사전/탐색 지위를 확인하게 한다.

완료 여부·잘못된 주장·도움이 필요했던 지점을 사전에 정해 기록한다. 실제 측정 전 성공률이나 시간 절감 수치를 제시하지 않는다.

## 최종 판단

현재 시각 디자인은 유지하고 **쉬운 입력 → 이유 있는 전체·집단 판정 → 맥락 있는 공유**를 강화하는 쪽을 권장한다. CRM 자동 발송·고객 DB·팀 권한·추가 통계 방법을 한꺼번에 늘릴 이유는 이번 관찰에서 확인하지 못했다. 최종 우선순위 확정과 실제 적용 판단은 사용자에게 남긴다.
