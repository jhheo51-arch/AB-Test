# 제품 방향과 범위

상태: 승인받은 방향을 정리한 설계안. 이 문서의 기능은 별도 표기가 없으면 **계획**이며 구현 사실이 아니다. 갱신: 2026-11-17 (Asia/Seoul).

**최신 보완:** [CRM 실험 판단 프레임 v0.2](FRAMEWORK_v02.md). A/B 승패를 기본 질문에 포함하고, CRM은 여정 목적 × 변경 요소로 세분화하며, 세그먼트는 대상·분석·적용을 연결하는 핵심으로 둔다. 이 문서와 함께 읽되 충돌하는 초기 설명보다 해당 최신 프레임을 우선한다.

## 1. 문제와 목표 사용자
- 첫 사용자: 통계 전담자가 상시 지원하지 않는 CRM 캠페인·고객 여정 실무자.
- 검토자: 분석 담당자와 캠페인·사업 책임자.
- 해결할 일: 전체와 사전 정의 고객 세그먼트의 A/B 승패·효과를 검토하고, 데이터 품질·측정 성숙도·사업 위험을 연결해 적용 범위와 결정을 기록.
- 첫 고객 맥락: JH Motors라는 가상 OEM의 시승 안내 실험. 실제 OEM 성과나 시장 수치를 뜻하지 않는다.

단순 p값 계산기, 범용 CRM, 전면 실험 실행 플랫폼은 첫 제품 정의에서 제외한다. ‘어떤 CRM 파일이든 자동 분석’도 약속하지 않는다.
CRM은 임시 진입 분야가 아니라 제품의 중심 범위다. 기본 CRM 여정 목적은 첫 행동·전환·유지·재활성화·관계/선호 관리로 구분하고, 비교 요소는 메시지·혜택·시점·빈도·채널·여정·접촉 유무로 분류한다. 모든 유형의 데이터·설계가 기본 통계 경로에 자동 적합한 것은 아니다.

## 2. 제품 구조: 데이터 객체와 사용자 작업을 구분
### 지속 저장할 객체
1. Company Profile: 고객 여정·채널·동의·데이터 원천·지점/재고/슬롯·원가·권한.
2. Experiment Contract: CRM 유형·질문·처치·대조·적격 대상·배정·지표·관측 창·표본·종료·전체/집단별 가설·비교 가족·사업 기준.
3. Segment Specification: 대상/분석/적용 역할·배정 전 기준시점·정의/버전·중첩/결측·정보량·사전/탐색 구분·집단 차이 검토 계획.
4. Evidence State: 출처·품질·성숙도·전체/집단별 효과·불확실성·승패·경쟁 설명·미확인 항목.
5. Decision Record: 결정·적용 세그먼트·근거/반대 근거·미해결 위험·승인자·모니터링·재평가.

값의 상태는 known / estimated / unknown / not_applicable / unsupported를 구분한다. 0·누락·미관찰·미지원은 같지 않다.

### 사용자가 수행할 여섯 작업
| 작업 | 핵심 질문 | 산출물 |
|---|---|---|
| 문제 정의 | 무엇을 바꿔 어떤 결정을 하려는가? | 문제·결정 질문 |
| 실험 설계 | 어떤 비교와 정밀도가 필요한가? | 버전 관리한 실험 계약 |
| 입력·의미 확인 | 열·키·분모·기간은 무엇인가? | 표준화된 데이터 정의 |
| 신뢰성 점검 | 어떤 추정이 가능하고 무엇이 막히는가? | 품질·성숙·지원 범위 보고 |
| 효과·승패·세그먼트 | 전체/집단별 A/B 중 누가 우세하고 차이의 근거는 무엇인가? | 효과·구간·승패·집단 차이/탐색 상태 |
| 사업 판단·기록 | 비용·위험·외적 타당성을 고려하면? | 사람 승인·다음 행동 |

이 여섯 작업은 화면 구성의 제안이다. 기존 G0~G8 진단을 삭제하는 새 체계가 아니라 그 진단을 사용자 작업으로 묶은 것이다.

## 3. 모듈 경계
```text
입력/열 매핑/데이터 정의
  → 설계·지원 범위 검증
  → 추정 대상별 품질·관측 성숙도
  → 버전 고정 통계 엔진
  → 전체 A/B 승패·세그먼트별 효과·집단 차이 검토
  → 사업 기준·가드레일 검토
  → 증거 기반 설명·보고서
  → 승인·변경·결정 이력
```

- 통계 엔진과 결정 규칙은 테스트 가능한 코드·명세로 만든다.
- AI는 질문·설명·보고서 초안만 보조한다. 수치 재계산, 데이터 채움, 원인 확정, 최종 승인에 사용하지 않는다.
- 결과와 설명은 데이터 버전·분석 방법·설정·경고에 연결한다.
- 사후 수정은 이력을 남기고 사전 설계로 위장하지 않는다.
- 식별키는 가명 키를 우선한다. 이름·전화·이메일 원문은 기본 입력에 요구하지 않는다. 보관·삭제·권한·처리 위치는 구현 전 별도 확정한다.

## 4. 첫 기본 분석 경로
| 축 | 권장 범위 |
|---|---|
| 비교 | A와 B 두 그룹. A는 기존 메시지 또는 미발송 등 명시적 비교 정책 |
| 배정 | 사용자 단위 무작위 배정이 문서와 기록으로 뒷받침되는 실험 |
| 결과 | 정해진 관측 창 내 사용자별 사건 발생 여부 |
| 기본 분석 | 고정 표본, 사전에 정한 가설 방향·유의수준·표본·종료 규칙 |
| 주지표 | 사전 지정 하나. 예약·클릭·시승 완료를 결과 보고 후 교체하지 않음 |
| 데이터 | 계약된 CSV와 설계 정보. 업로드 단추만으로 타당성이 보장되지 않음 |
| 세그먼트 | 배정 전 사전 정의 주요 축부터 설계·비교·적용 범위에 연결. 검정·정보량·다중성은 별도 검증 |
| 출력 | 전체/집단별 절대차·상대차·구간·p값·승패·품질·성숙도·집단 차이 검토 상태·결정 기록 |

정확한 통계 방법은 실제 구현 전 검증 명세로 고정한다. 기존 Newcombe 구간·pooled z 분석 자산을 참고할 수 있지만, 낮은 사건 수·극단 비율·0 분모·근사 부적합 처리는 별도로 검증해야 한다. 상대 변화율 구간을 절대차 구간의 단순 나눗셈으로 만들지 않는다. 비지원 조건에서는 다른 검정을 AI가 임의 선택하지 않는다.

### 배정과 노출
실제 읽음·클릭·전달 성공 고객만 골라 주효과를 비교하지 않는다. 기본은 배정 기준 분석이며 노출·전달은 별도 진단이다. 그룹 열이 있다는 사실만으로 무작위 배정이 확인됐다고 하지 않는다.

### 가드레일
‘수신 거부 증가가 유의하지 않다’를 안전으로 바꾸지 않는다. 허용 손실·안전 기준이 없으면 unknown으로 남긴다. 비열등성·동등성 확증을 제공하려면 해당 설계·방법을 별도 지원하고 검증해야 한다. 법·동의·중대 안전은 이익 점수로 상쇄하지 않는다.

### 품질 영향
지표마다 오류 영향이 다를 수 있다. 클릭 로그 장애가 독립된 시승 원장 기반 결과를 자동으로 무효화하는 것도, 반대로 무시해도 된다는 것도 아니다. 영향을 받는 추정과 주장만 명시적으로 제한하며 영향이 미확인인 결론은 보류한다.

## 5. 입력의 최소 개념
experiment_id / 가명 subject_id / assigned_arm / assigned_at / 원천 및 지표 정의 / result_event 또는 사용자별 집계 / 관측 마감시각.
실험 계약에는 배정 확률·적격 조건·관측 창·종료 규칙·지표 역할·데이터 생성/추출 버전을 기록한다. 구현 전 파일 스키마와 시간대·결측 코드를 확정해야 하며 이 목록을 확정 API 스키마로 보지 않는다.

세그먼트의 정의·기준시점·역할·버전은 핵심 설계 정보다. 집단별 분석에는 해당 속성·누락 처리·분모가 필요하며, 없는 집단 정보를 AI가 만들어 넣지 않는다. 전달·노출·매출·비용은 목적에 따라 추가한다. 필요한 자료가 없으면 그 결론은 미지원 또는 불충분이다. 관측 기간이 지나지 않은 고객을 단순 0으로 확정하지 않는다.

## 6. 결과와 결정의 분리
- 데이터/방법 상태: valid / limited / invalid / unsupported / immature.
- A/B 승패: A 우세 근거 / B 우세 근거 / 승패 보류 / 판정 불가. 사전 주지표·가설 방향·방법·기준에 한정한다. 높은 점추정은 승리와 다르고 비유의성은 동등성 증명이 아니다.
- 세그먼트 상태: 집단별 결과 / 집단 차이 근거 / 탐색 신호 / 정보 부족. 전체 결과와 병기하고 X 유의·Y 비유의만으로 효과 차이를 확정하지 않는다.
- 효과 상태: 개선 근거 / 악화 근거 / 불확실. 비열등·동등은 별도 지원 설계에서만.
- 사업 근거 상태: 확인 / 추정 / 미확인 / 해당없음.
- 결정 후보: 도입 검토 / 기존안 유지 / 재설계·후속 실험 / 판단 보류.
- 실제 결정: 사람의 승인, 이유, 적용 범위, 감시·롤백·재평가 조건.

품질 통과는 사업적 성공이 아니고, 유의성 통과는 출시 허가가 아니다. 보류에는 필요한 증거·담당자·재검토 조건을 붙인다. 더 모으면 유의해질 것이라는 이유로 사전 규칙 없는 연장을 권하지 않는다.

## 7. 첫 버전 제외 범위
실제 발송, SDK·서버 배정, 실시간 배포/롤백, 임의 CRM API, 관측자료의 자동 인과 추론, 군집·가구·전환 설계, A/B/n, 일반 연속형 이익/매출 검정, 순차 검정·밴딧, 자동 사후 세그먼트 확정, 장기 LTV 확정 추정.

미지원은 요청을 잘못 계산하지 않는 경계다. 필요성이 확인되면 방법·데이터·시험 기준을 추가하고 지원 범위를 넓힌다.

## 8. TRI-V의 위치
Variable Control=설계·품질, Vector Segmentation=전체 효과와 사전 정의 이질성 검토, Value-Linked Decision=사전 사업 기준과 사후 판단 기록.
세그먼트 설계·집단별 A/B 효과 검토·적용 범위는 초기 핵심에 포함한다. 집단 간 효과 차이의 확증에는 사전 계획·정보량·상호작용 등 적절한 방법·다중 비교 통제와 검증이 필요하다. 미지원이면 탐색/정보 부족으로 표시하고 기능 완성을 주장하지 않는다. TRI-V는 새 통계 검정을 대체하는 검증된 이론이 아니라 저자 제안 작업 프레임이다.

## 9. 확장 순서와 완료 기준
1. 기본 경로: 알려진 기준과 일치하는 계산, 잘못된 입력·미성숙·미지원 차단, 재현 가능한 보고.
2. CRM 판단 지원: 지표 충돌·관계 위험·운영 용량·사업 가정, 사용자 이해 테스트.
3. 데이터 연동: 고객 키·동의·권한·지표·갱신 규칙과 원천 대조 검증.
4. 실험 실행: 지속 배정·노출·로그·QA·중단·롤백 검증.
5. 고급 설계: 방법별 오류율·포함확률·검정력·선택/종료 편향을 시험한 후 추가.

기능 수가 아니라 검증한 범위로 다음 단계 진입을 결정한다. 합성 데이터는 생성 가정·시드를 고정하고 효과 없음·알려진 효과·측정 오류·미성숙 시나리오를 사용한다. 유리한 결과가 나오는 시드를 고르지 않는다.

## 10. 현 단계 성공과 미확인
문서의 성공 기준은 구조·대상·범위·사람 승인 경계의 명료성이다. 아직 사용성·정확성·매출 효과·지불 의사·경쟁 우위가 검증된 것은 아니다. 다음 개발 결정 전에 실제 잠재 사용자에게 CSV 준비·문제 진단·보고서 검토 작업을 수행하게 하고 기존 워크플로우와 비교한다.
